- 일자: 2026-08-11 · 환경: 로컬 CPython 3.14.5 (Windows) — Pyodide 실측은 하단 참고
- 기획안 검증 과제 [최우선] "Tracer 스파이크"의 결과. Go/No-Go 판정 포함

## 발견 1 — 스텝 폭발의 실체: 개수보다 직렬화 크기

- 학습 규모 코드의 이벤트 수는 수백~수천 (fib(15)에 7,896). **우려했던 "수십만" 폭발은 학습용 코드에선 나타나지 않음.**
- 진짜 병목은 **직렬화 크기**: 이벤트당 평균 185~435바이트 → fib(15) 하나가 1.4 MB. 20만 이벤트 상한을 채우면 ~40 MB로 메모리·전송이 먼저 무너진다. **기획안의 3중 상한(maxEvents + maxSerializedBytes + maxRuntime) 필요성이 수치로 입증됨.**
- LLM 입력으로 raw trace는 불가 (1 MB+) → **Digest 압축 계층의 필요성 실증.**

## 발견 2 — 오버헤드는 훅이 아니라 상태 직렬화에서 나온다

- settrace 배율(35×~1,732×)은 커 보이지만 절대값은 학습 코드에서 **수십 ms** — UX 문제 없음.
- 배율이 가장 큰 샘플(중첩 dict)은 이벤트 수가 가장 적다 = 비용의 지배 요인이 훅 호출이 아니라 **매 스텝의 스냅샷 직렬화**라는 뜻.
- 따라서 성능 개선의 우선순위는 훅 교체(monitoring)가 아니라 **직렬화 최적화**(변경 가능성 선필터, 캐시)다.

## 발견 3 — sys.monitoring으로도 상태 수집은 성립한다

- 콜백에 frame이 오지 않는 문제는 `sys._getframe(1)` 우회로 해결되며, 전 샘플에서 **locals 확보율 100%**.
- 단 call/return/exception을 별도 이벤트로 등록해야 하고 frame 접근이 간접적이라 구현 복잡도가 높다.
- 훅 자체의 오버헤드는 monitoring이 훨씬 낮으나(0.2~2 ms), 발견 2에 따라 전체 성능의 지배 요인이 아니므로 이점이 제한적.

## Go/No-Go 판정

**Go — MVP는 `sys.settrace` 유지.** 상태 수집이 단순·안정적이고(프레임 직수령), 성능 병목은 훅이 아니므로 monitoring 전환의 실익이 없다. monitoring은 직렬화 최적화 이후에도 병목이 남을 경우의 확장 카드로 보존한다. (기획안 리뷰의 판단 원칙 "성능이 다소 느려도 상태 수집이 단순하면 settrace"와 일치)

## Pyodide 환경 참고 실측

- Slice 1 E2E에서 무한 루프 5,000이벤트 수집이 10초 타임아웃 내 완료 (브라우저·WASM).
- 학습 예제(6~20이벤트)는 체감 즉시. 웜 스타트에서 실행 단계는 1초 미만.

## 제안: MVP acceptance criteria 초안 (기획안 "스파이크 후 수치 고정" 이행)

| 지표 | 제안 기준 | 근거 |
|---|---|---|
| maxEvents | 20,000 (기존 5,000 상향) | fib(15)=7,896이 잘리지 않아야 함. 20k×~300B ≈ 6 MB로 안전 |
| maxSerializedBytes | 10 MB | 위 표 이벤트당 크기 기반 |
| maxRuntime | 10초 유지 | E2E 실측상 여유 충분 |
| 웜 E2E (실행→재생 시작) | P50 ≤ 2초, P95 ≤ 5초 (LLM 제외) | 로컬 수십 ms + Pyodide 배수 감안 |
| Tracer 정확성 | 벤치마크 셋 이벤트 검증 100% | tracer_test 6종 전부 통과 중 |

*이 기준은 벤치마크 셋(50~100개) 구축 후 유형별로 재검증하여 확정한다.*
